# Architecture

## Overview

```
Browser ──► Next.js (Vercel)
              ├─ proxy.ts            refreshes the Supabase session cookie; gates /account /host /admin
              ├─ Server Components    read data as the signed-in user (RLS applies)
              ├─ Server Actions       validate with Zod, then call Supabase / RPC functions
              └─ lib/supabase/admin   service-role client — server only, used after a permission check
                     │
                     ▼
            Supabase: PostgreSQL (+RLS) · Auth · Storage
```

The browser never talks to privileged APIs. Anything that changes money, status or availability goes through a `SECURITY DEFINER` database function that re-checks the caller (`auth.uid()`), or through server code with the secret key.

### Booking lifecycle

```
            instant                     payment verified (Phase 5)
 create ──────────────► AWAITING_PAYMENT ──────────────► CONFIRMED ─► CHECKED_IN ─► COMPLETED
   │  request                  │ hold expires / cancel
   └────────► PENDING ─────────┤──────► EXPIRED / CANCELLED   (dates released)
                 │ host accepts └► AWAITING_PAYMENT
                 └ host declines ──► REJECTED                   (dates released)
```

Statuses `PENDING, AWAITING_PAYMENT, CONFIRMED, CHECKED_IN, DISPUTED` hold inventory. The `bookings_no_overlap` exclusion constraint makes overlapping live bookings on one unit impossible. `create_booking` additionally locks the unit rows (`FOR UPDATE`), expires stale holds, checks host blocks, then inserts; if a concurrent request wins, it moves on to the next free unit of the same room type.

`expire_stale_bookings()` should run every few minutes (Phase 4 adds a Vercel Cron route). Until then, holds are also expired on demand whenever someone tries to book the same unit, and searches already ignore expired holds.

### RPC functions callable from the app

| Function | Who | Purpose |
|---|---|---|
| `search_properties(...)` | anyone | Filtered, sorted, paginated search over approved listings, availability-aware |
| `quote_booking(listing, check_in, check_out, adults, children, infants)` | anyone | Full price breakdown |
| `listing_is_available(listing, check_in, check_out)` | anyone | Availability of one unit |
| `create_booking(property, unit_group, ...)` | signed-in, verified email | Atomic reservation |
| `host_respond_booking(booking, accept, reason)` | the host | Accept/decline a request |
| `cancel_unpaid_booking(booking, reason)` | guest/host | Cancel before payment |

## Security checklist (implemented)

- Roles stored in the database; server-side checks in `dal.ts`; triggers block self-promotion.
- RLS on every table; money, ledger, audit and booking tables are read-only to clients.
- Secret key only in `lib/supabase/admin.ts`, protected by `import "server-only"`.
- Zod validation on every server action; DB check constraints as a second layer.
- Login, sign-up and reset are rate-limited (in-memory now; swap to Redis/KV at scale).
- Open-redirect protection on `next=` parameters.
- Sign-up responds identically for new and existing emails (no account enumeration).
- Security headers (`X-Frame-Options: DENY`, `nosniff`, referrer and permissions policies).
- Private bucket + signed URLs for CNIC and ownership documents.

## Payments (Phase 5 design)

A `PaymentProvider` adapter interface (`initiate`, `verify`, `parseWebhook`, `refund`) with a clearly labelled **sandbox** provider. Each provider's API, merchant and marketplace/split-settlement eligibility, currencies and webhook signing must be confirmed from its current official documentation before integration. Webhooks are stored in `webhook_events` (unique per provider + event id) so duplicates are ignored, and a booking is confirmed only from a verified server-side status — never a browser redirect.

## Known limitations / next steps

- Supabase TypeScript types are hand-written in `src/types/db.ts`; regenerate with `npx supabase gen types typescript` once connected.
- Search map view (multiple pins) is planned with the maps provider choice; destination and property pages already show maps.
- Long-form pages (Terms, Privacy, Help) are English-only for now; UI chrome is fully translated.
